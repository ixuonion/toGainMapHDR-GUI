# 性能审计与优化记录

## 处理链路

1. SwiftUI 负责文件选择、参数配置、进度和日志展示。
2. `HDRConverterViewModel` 快照转换参数，并通过受限任务组调度多个子进程。
3. 每个子进程运行内嵌 `toGainMapHDR`，使用 Core Image 解码 HDR 图像、计算 SDR 基础图和 Gain Map。
4. Core Image / ImageIO 使用系统 HEIF 编码器写出 HDR Gain Map 文件。

GUI 不直接解码或转换图片。核心像素处理继续由内嵌 CLI 和 Apple 系统框架完成。

## 已确认瓶颈

- 原自动模式按 CPU 核心数启动子进程。在 18 核设备上会同时创建 18 个独立 `CIContext`，大图转换时内存和 HEIF 编码资源压力过高。
- 33MP 16-bit TIFF 的单进程峰值常驻内存约 3.6GB，不能按普通 CPU 任务估算并发。
- SwiftUI 重绘会重复读取所有输入文件的磁盘属性。
- 子进程输出缓冲区存在并发读写风险；取消可能发生在进程注册和启动之间。
- 取消时进度窗口会提前关闭，而后台进程仍可能尚未退出。
- 打包和运行时检查仍引用旧的根目录资源位置。

## 真实素材基线

设备：Apple M5 Max，18 核 CPU，36GB 内存。

素材：4 张 Sony 4672x7008 16-bit TIFF，默认 ISO Gain Map HEIC 参数。

| 并发 | 墙钟时间 | 相对顺序吞吐 |
| --- | ---: | ---: |
| 1 | 73.97 秒 | 1.00x |
| 2 | 37.21 秒 | 1.99x |
| 4 | 19.14 秒 | 3.86x |

顺序与 2 并发的 HEIC 输出逐字节一致。4 并发输出可正常解码且 Gain Map
类型、尺寸、Headroom、GainMapMax/Min 均一致，但 Apple 系统 HEIF/HEVC
编码器在多个同时编码会话下会生成不同大小和哈希的码流。最小 Core Image
实验在完全移除 Gain Map 计算后仍能复现，因此该差异不是 GUI 或 Gain Map
算法的数据竞争。

对 4 张测试图分别执行 Apple SDR 和 HDR 解码，并逐一比较约 9822 万个 RGB
通道样本，MAE、RMSE 和最大误差均为 0。因此当前证据只表明 4 并发会破坏
文件的字节级可复现性，不能证明它额外降低了可见画质。HEIF 本身仍是有损格式，
但“文件不同”不等于“解码像素不同”。

为满足严格输出兼容要求，自动和手动模式均限制为最多 2 并发。

## 已实施策略

- 自动并发综合芯片架构、活动核心数、物理内存和文件数，Apple Silicon 默认最多 2，Intel 默认 1。
- 手动并发范围限制为 1-2，实际值仍按 75% 物理内存安全上限钳制。
- 批次启动时快照输入列表、参数、可执行路径和并发值。
- 文件大小只在输入列表变化时读取并缓存。
- 子进程输出使用加锁缓冲区；启动与取消通过同一把锁消除竞态。
- 取消后等待全部已启动进程结束，再关闭进度窗口并汇总结果。
- 日志记录批次耗时、完成数、并发数和每分钟吞吐。
- 修复运行时检查和 Release 打包的资源路径、扩展属性与本地签名流程。

## 后续方向

- 使用 Instruments/ETTrace 对 Core Image、GPU 和 HEIF 编码阶段分别采样。
- 在不要求字节级输出一致时，按图像尺寸和系统内存压力动态尝试 3-4 并发。
- 将 CLI 建成独立 Xcode target，并建立 Vendor 源码与内嵌通用二进制的可重复构建和哈希校验。
- 为各输出模式建立自动化样本集，验证 Gain Map 辅助数据、色彩空间、位深和元数据。

## maxLuminance 源码一致性

上游同步版本使用整幅 `CIAreaMaximum`。本仓库提交 `18d5071` 曾把图像缩到
最长边 512 像素，再将结果除以几何缩放比例。几何缩放不会同比改变像素亮度，
因此该反除会将 headroom 错误放大，并使结果依赖输入分辨率。

GUI 当前内嵌的预编译 CLI 实际仍采用上游算法；错误只存在于 Vendor 源码，
导致未来从源码重建时输出变化。Vendor 已恢复为上游整幅计算逻辑，使源码与
当前运行二进制的算法重新一致。
